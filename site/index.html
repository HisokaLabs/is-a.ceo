How it works

  1. Fork the registry repository.
  2. Add a JSON file named after what you want: {{registry_dir}}/<subdomain>.<zone>.json, for example freelancer.{{zone_example}}.json.
  3. Open a pull request. A bot previews the exact DNS change and comments it on the PR.
  4. Once it is merged, {{actions_repo}}@{{actions_version}} pushes the zone through {{dns_tool}} and this page rebuilds.

What can I point it at?

The default is GitHub Pages, so a name works the moment it merges with no configuration at all. Everything else needs a record: a Vercel or Netlify deploy, a VPS, a Notion page behind a CNAME, an API, or whatever you are actually shipping. The title on the card is the only place a job title is required.

{{registry_dir}}/freelancer.{{zone_example}}.json 
{
  "domain": "{{zone_example}}",
  "subdomain": "freelancer",
  "owner": "your-github-username",
  "repo": "github.com/you/landing",
  "description": "Founder, visionary, occasional shipper",
  "records": {
    "CNAME": ["cname.vercel-dns.com"],
    "TXT": ["resend._domainkey=your-key-here"]
  }
}

Supported record types: A, AAAA, CNAME, TXT, MX, NS, SRV, CAA and PTR. Mix and match freely inside one file. The subdomain may also be dotted (_acme-challenge.app) or a wildcard over a base you already claim (*.app).

Rules, briefly

  • One subdomain per person per zone, per purpose. No squatting, no hoarding.
  • No malware, phishing, or anything that would get the whole zone delisted.
  • Keep the content at your subdomain legal in {{jurisdiction}}, where the zones live.
  • Abuse reports go to {{contact_email}}.

Full details live in CONTRIBUTING.md.
